PoC trust architecture

One public code. Separate consent for every relationship.

The identity code is a locator—not a container for personal information. A requester first sees only the open profile. The receiver may approve the connection, choose private fields, define an expiry and revoke access later.

1Share locator

QR, NFC or memorable HumanLink code contains only a routing identity.

2Request consent

The requester shares an open identity and purpose for connecting.

3Approve scope

The receiver chooses open-only or selected private fields and expiry.

4Encrypt grant

A fresh AES content key encrypts the approved payload for that requester.

5Revoke anytime

The owner can invalidate the relationship grant without changing the public code.

↔

Directional by default

Approving another person does not automatically give you access to their private vault. They must separately approve you.

🔑

Per-relationship keying

Each approved private package has its own content key. A compromise of one grant should not expose every relationship.

◌

Public updates without exposure

Open profile updates can continue to sync while phone, email and meeting links remain sealed.

Important production boundary: this browser PoC stores demonstration private keys in localStorage so multiple people can be simulated on one device. A real deployment must use secure device keystores, authenticated backend services, signed and expiring tokens, anti-abuse controls, account recovery, legal consent records, rate limits and independent security review.
